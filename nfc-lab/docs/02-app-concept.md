# 02. 앱 컨셉 — 「TapNote (탭노트)」

> **폰 두 대를 맞대면 쪽지가 날아간다.**
> 보내는 폰은 카드(HCE)인 척, 받는 폰은 리더인 척. Android Beam이 죽은 시대의 정석 P2P 패턴.

## 1. 사용 시나리오

```
[민지 폰]                         [유찬 폰]
"보내기" 탭에서                    "받기" 탭 열어둠
"오늘 회의 3시로 변경!" 입력        (Reader Mode ON, 스캔 대기)
    │                                 │
    └──── 두 폰 등짝을 맞댄다 ────────┘
                  │
         ⚡ 1초 이내 전송 완료
                  │
              [유찬 폰]
        "📩 오늘 회의 3시로 변경!"
```

## 3. 역할 분담

| 역할 | 폰 | 안드로이드 컴포넌트 | 하는 일 |
|------|-----|--------------------|---------|
| 카드 (보내는 쪽) | A | `HostApduService` | AID SELECT 받으면 응답, READ 명령에 쪽지를 잘라서 전달 |
| 리더 (받는 쪽) | B | `NfcAdapter.enableReaderMode` + `IsoDep` | 태그(=폰 A) 감지 → SELECT → READ 반복 → 쪽지 조립 |

## 4. TapNote 통신 프로토콜 v1 (우리가 설계하는 부분!)

### 4.1 AID

```
F0 54 41 50 4E 54          (6바이트)
│  └─────────────┘
│   "TAPNT" ASCII
└ F0 = proprietary(사설) AID 프리픽스
```

### 4.2 명령 셋

**① SELECT (통신 시작) — 리더 → 카드**

```
00 A4 04 00 06 F0544150 4E54 00
```

카드 응답: `54 50 01` + `90 00`
(매직 "TP" + 프로토콜 버전 1 — "나 TapNote 맞아, v1으로 말하자")

**② GET_INFO (쪽지 메타데이터) — 리더 → 카드**

```
80 01 00 00 00
│  └ INS 0x01 = GET_INFO
└ CLA 0x80 (사설 명령 클래스)
```

카드 응답: `[전체 길이 2바이트, big-endian] [청크 수 1바이트]` + `90 00`

**③ READ_CHUNK (쪽지 조각 읽기) — 리더 → 카드**

```
80 02 <chunkIndex> 00 00
│  │   └ P1 = 몇 번째 조각? (0부터)
│  └ INS 0x02 = READ_CHUNK
```

카드 응답: `[UTF-8 쪽지 조각, 최대 200바이트]` + `90 00`

**에러 상태 코드**

| SW1 SW2 | 의미 |
|---------|------|
| `90 00` | 성공 |
| `6A 82` | SELECT한 AID가 우리가 아님 / 보낼 쪽지 없음 |
| `6A 86` | 잘못된 chunkIndex |
| `6D 00` | 모르는 INS |

### 4.3 전체 통신 흐름 (쪽지 500바이트, 청크 200바이트 기준)

```
리더(받는 폰)                          카드(보내는 폰)
    │ ── SELECT F0544150 4E54 ──────────▶│
    │ ◀────────── "TP" v1 + 9000 ────────│
    │ ── GET_INFO ──────────────────────▶│
    │ ◀── len=500, chunks=3 + 9000 ──────│
    │ ── READ_CHUNK(0) ─────────────────▶│
    │ ◀── [200바이트] + 9000 ────────────│
    │ ── READ_CHUNK(1) ─────────────────▶│
    │ ◀── [200바이트] + 9000 ────────────│
    │ ── READ_CHUNK(2) ─────────────────▶│
    │ ◀── [100바이트] + 9000 ────────────│
    │        (조각 3개 조립 → UTF-8 디코딩 → 화면 표시 🎉)
```

### 4.4 설계 결정 이유

- **왜 청크로 쪼개나?** ISO-DEP 한 번의 응답 APDU는 안전하게 ~256바이트. 긴 쪽지는 나눠 보내야 함
- **왜 GET_INFO가 먼저?** 리더가 몇 번 READ해야 하는지 미리 알면 루프가 단순해지고, 진행률 표시도 가능
- **왜 매직 바이트 "TP"?** 다른 HCE 앱을 잘못 SELECT했을 때 즉시 구분하기 위해

## 5. 기술 스택 확정

| 항목 | 선택 |
|------|------|
| 언어 | Kotlin |
| 최소 SDK | API 26 (Android 8.0) — HCE는 API 19부터라 여유 |
| UI | 단일 Activity + 탭 2개 (Fragment 없이 심플하게) |
| 카드 역할 | `HostApduService` 상속한 `TapNoteCardService` |
| 리더 역할 | `NfcAdapter.enableReaderMode` + `IsoDep` |
