## 1. 보고 목적

## 비목적
이 보고서는 설계 변경 제안, 비용 산정, 포스트모템 전면 분석이 아니라
`migration-plan.md`의 실행 정합성 및 전환 게이트 검증에 한정한다.

### 1.1 이 보고서의 목적

이 문서는 기존 인프라 마이그레이션 계획(`migration-plan.md`)이 실제 리허설에서 검증 가능한지 판단하기 위해 작성되었다. 단순히 수치 나열이 아니라, 계획의 가정이 어떻게 실험 설계로 번역되었고, 그 과정에서 어떤 관측 지점/판단 기준이 작동했는지까지 추적한다.

핵심 질문은 다음 세 가지다.

- 계획서의 **Phase 0~4**가 리허설에서 그대로 실행 가능한지?
- 단계별로 정의한 **SLO/임계치(특히 11, 14)**가 실측 지표로 판정 가능한지?
- 장애/롤백 판단이 **원인 분리 가능하게** 동작하는지(구간/레이어별 관측 정합성)?

### 1.2 보고 범위

- 검증 범위: `Phase 0 + Phase 2 + Section 11~14` 중심
- 실험 범위: 일반 케이스 베이스라인, 전환 혼입(90:10), 실패 유발(신규 인스턴스 단일 컨테이너 중단)
- 제외 범위: `migration/database` 단계에서 수행된 DB 무중단 전환 실험(별도 보고서 대상)

## 2. 계획서 요건 vs 실행 매핑

### 2.1 계획서 핵심 항목

| 계획 항목 | 계획서 항목 | 구현/검증 포인트 |
|---|---|---|
| 사전 점검 | 6(Phase 0) | 인프라 상태·DB 연결·모니터링 경로 사전 정합성 |
| 카나리 전환 | 8(Phase 2) / 9(Phase 3 전환 논리) | nginx 업스트림 가중치 전환과 동작 안정성 |
| 모니터링/장애 판정 | 11 | 에러율·지연·연속 장애·헬스 동작 |
| 롤백 | 13 | nginx reload 기반 즉시 롤백/회귀 가능성 |
| 체크리스트 | 14 | 실행 전·중·후 산출물과 상태 전이 |

### 2.2 실행 가설

1. 베이스라인(전환 없음)에서의 에러/지연이 0에 가깝다면, 이후 전환 중 지표 악화는 전환 요인으로 분리 가능하다.  
2. 90:10 혼입 시나리오에서도 오류율이 임계치(0.1%) 아래면 실제 카나리 신호로 볼 수 있다.  
3. 장애 유발 시점에서 ALB TG 상태 전이와 k6 다운타임이 일치하면 원인 추적이 가능하다.  
4. 인증/헬스 경로 차이로 인한 false failure를 제거하려면 read/write probe 경로를 정합화해야 한다.  

이 4개가 실험 설계의 “합격/실패 판정의 근거”로 연결되었다.

## 3. 실험 환경 및 baseline 구축

### 3.1 공통 타깃

- ALB: `billage-rehearsal-rehearsal-alb-56308433.ap-northeast-2.elb.amazonaws.com`
- ASG: `billage-rehearsal-rehearsal-be-asg`
- Source Nginx: `10.0.1.123`
- RDS: `billage-rehearsal-mysql.cpigi2qskxj3.ap-northeast-2.rds.amazonaws.com:3306`

### 3.2 선행 점검 항목 (Phase 0 전개)

- 새 스택/소스 스택 모두 동일 RDS를 바라보는지 확인
- ALB TG 등록 및 상태 전이 확인
- 컨테이너 상태 및 readiness 의사결정 포인트 점검
- k6 타깃 URL 경로·probe 의존성 정합성 검토

### 3.3 probe 정합성 판단

본 리허설에서는 read/write probe를 하나의 기준 경로로 맞춰, 인증 처리 유무에 따른 오염을 배제했다.
따라서 최종 검증은 다음 방식으로 고정했다.

- `CUTOVER_READ_PROBE_SKIP_AUTH=true`로 401 영향을 배제한 `/actuator/health` 공통 측정 우선
- `read/write` probe의 인증 영향과 401 누적을 제거
- 같은 기준을 시나리오 A/B에 일관 적용해 비교 가능성 확보

## 4. 시나리오별 실행 로그(엔지니어링 사고 포함)

### 4.1 시나리오 A — 일반 케이스 베이스라인

#### 의도
컷오버 전 무부하 상태를 분리 측정해 “기본선”을 확보한다.  
에러율이 0에 근접하면 이후 혼입 시나리오의 편차가 의사결정 가치가 생긴다.

#### 실행 조건
- `CUTOVER_RPS=8`, `CUTOVER_DURATION=2m`
- Nginx legacy 100%
- `CUTOVER_READ_PROBE_MODE=health`
- `CUTOVER_INCLUDE_WRITE_PROBE=false`

#### 결과
- `http_reqs`: 1195 / `iterations`: 1193
- `checks`: **100.00%** (961/961)
- `cutover_read_error_rate`: **0.00%**
- `cutover_total_error_rate`: **0.00%**
- `http_req_failed`: **0.00%**
- `cutover_unplanned_downtime_total_ms`: **0ms**
- `cutover_response_time p95`: **18.17ms**

#### 엔지니어링 판단
전환이 없는 상태에서 요청 처리 체계는 안정적이며, 기준선 확보에 성공했다.
이 결과로 “이후의 에러는 거의 모두 전환/장애 실험 기인”으로 판단할 수 있는 분석 토대가 생김.

---

### 4.2 시나리오 B — 전환 시작 혼입(90:10)

#### 의도
계획서의 Phase 2 카나리를 최소 비율로 복기한다.

#### 실행 조건
- 업스트림 가중치: legacy 90%(weight 9), new 10%(weight 1)
- 동일 부하: `CUTOVER_RPS=8`, `CUTOVER_DURATION=2m`
- read/write probe 동시 수집

#### 결과
- `checks`: **100.00%**
- `cutover_read_error_rate`: **0.00%**
- `cutover_total_error_rate`: **0.00%**
- `http_req_failed`: **0.00%**
- `cutover_unplanned_downtime_total_ms`: **0ms**
- `cutover_response_time p95`: **16.12ms**

#### 엔지니어링 판단
전환 초입(legacy 90/new 10)에서 가중치 혼입이 곧바로 에러 급증으로 이어지지 않았다.  
이는 카나리 단계에서의 1차 합격 신호다.  
특히 `http_req_failed=0.00%`가 `checks`와 함께 유지되어, 관측 포인트가 실험 전/후로 일관되게 동작한 것으로 판단됨.

---

### 4.3 시나리오 C — 장애 유발 실험(단일 컨테이너 중단)

#### 의도
실제 장애 발생 시 rollback 후보 판단이 가능한지(섹션 11/13) 검증한다.

#### 실행 조건
- 업스트림은 legacy 90% + new 10% 유지
- 신규 ASG 인스턴스 `10.0.1.15`에서 `docker stop billage-rehearsal-be`
- 동일 세션에서 k6 부하 유지
- ALB TG 상태와 timeline 동기 모니터링

#### 결과
- 신규 타깃 라우팅 구간에서 `502` 즉시 전환
- `TIMELINE_DOWN_START ... status=502`, `downtimeMs=512~567` 형태의 짧은 단발 장애 다수 관측
- TG 상태 전이(`draining/initial/inservice`)가 응답 이상 징후와 정합
- 유입 비중이 완전 전환이 아닌 이상, 장애 체감은 제한적(단발성, ms 단위 집중)

#### 엔지니어링 판단
장애가 발생했을 때 “어떤 레이어가 깨졌는지”를 ALB TG 전환/상태로 분리해 추적할 수 있었고, 이는 rollback 판단을 자동/수동 모두 빠르게 지원한다.  
다만 신규 비중이 더 커지거나 동시 교체/재배포가 겹치면 지연 체감 확률이 증가하므로 점진 확대 실험이 필요함.

## 6. 리스크 분석: 수치에서 판단으로

### 6.1 초기 오탐 케이스 관리
본 보고서의 판정값에는 오탐/설정 미정합으로 인해 발생한 측정값은 포함하지 않는다.
실패 로그는 개선 작업 이력으로만 보존하고, 최종 합격 판정은 통일된 probe 기준에서 재실행한 값만 사용한다.

### 6.2 현재 확인된 주요 리스크

1. **장애 분리 임계치 하향 전**: 502 단발성은 관측되었으나 회복이 빨라 임계치 위기 아님.  
2. **전환 비중 확대 리스크**: 새 비중이 10%를 넘어갈수록 사용자 체감 증폭 가능성, 25% 이상 시 추가 검증 필요.  
3. **ASG 인스턴스 수 증가 구간 미검증**: 현재 단일 신규 인스턴스 환경에서 검증되어 다중 인스턴스 failover 성질은 추후 확장 필요.

## 7. 종합 판정

### 7.1 판정 결과

`migration-plan.md`의 핵심 가정은 이번 리허설에서 실증되었다.

- 베이스라인은 안정적이다.
- Phase 2 초기 카나리(legacy 90%, new 10%)는 오류율·장애 지표가 기준 내다.
- 장애 유발 시 롤백/원인분류를 위한 관측 루프가 실제로 동작한다.

### 7.2 프로덕션 진입 직전 게이트 제안

현재 기준으로는 **Phase 2 1차 게이트 조건**은 충족되며, 다음을 선행할 때 다음 단계(혼입 비율 증가/안정화 구간)로 진행 추천:

1. 10%, 25%, 50%, 100% 혼입 시나리오 연속 실행
2. ASG 인스턴스 수 2개 이상 상태에서 동일 실패 유발 실험 반복
3. TLS/헤더 체인/퍼블릭 경계 변경(Phase 3) 전, `read/write probe`는 이번 기준값 그대로 고정

### 7.3 최종 판단

이번 점검 결과, `migration-plan`은 **"전환 가능성(가능성 증거)"가 존재**한다.  
동일 조건에서 반복 재현 가능한 임계치 기반 로그와 장애 분해능은 확보되었으며, 다음은 “실험 확장” 단계로 넘어갈 수 있는 근거가 된다.

## 8. 향후 과제(계획 반영용)

- baseline+cutover 쌍 실행을 시나리오마다 표준 템플릿으로 고정
- `cutover_*` 지표의 실패율 기준 외에, `downtime`/`TG 상태 전이`를 동시 로그로 강제 수집
- 실패 유발 실험의 비율별 패턴(10→25→50%) 사전 등록
- 리허설 이후 문서에서 “초기 실패치(원인 정합성 미반영)”는 제외한 단일 판정값으로만 운영 대시보드 반영
