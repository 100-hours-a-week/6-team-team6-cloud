# 무중단 인프라 마이그레이션 계획서 (최종본)
EC2 단일 인스턴스 → ALB + ASG 구조 전환  
Billage C2C 렌탈 플랫폼

| 항목 | 값 |
|---|---|
| 작성일 | 2026-03-02 |
| 대상 서비스 | Billage C2C 렌탈 플랫폼 |
| 현재 구조 | DNS → EC2(EIP) → Nginx → Spring Boot → RDS |

## 근본 목적
기존 EC2 기반 단일 엔드포인트에서 신규 ALB + ASG 기반 경량 인프라 전환으로 안전하게 이동하기 위한 실행 계획을 정한다.

## 비목적
요금 정책 확정, 신규 기능 배포, 영구 운영 자동화 설계는 본 문서 범위 밖으로 둔다.

## 1. 범위와 전제

DB는 이미 EC2 MySQL에서 RDS로 마이그레이션을 완료했다. Native Replication을 통해 실시간 동기화를 유지하면서 전환했고, 만일의 사태에 대비한 역복제 구성까지 갖춰놓은 상태다. 이 문서는 그 다음 단계인 인프라 전환을 다루며, 사용자 트래픽이 레거시 EC2에서 신규 ALB+ASG 구조로 이동하는 과정을 계획한다.

전제는 다음과 같다.

- DB 마이그레이션에서 역복제로 “즉시 롤백”을 보장했다.
- 인프라 전환에서도 동일한 수준의 롤백 안전성을 확보한다.
- 전환/롤백 스위치는 **통제 가능하고 수 초 내 반영되는 계층**에 둔다.
- DNS 변경은 최종 구조의 퍼블릭 엔드포인트를 고정하기 위한 **1회 작업**으로만 수행한다.

> **설계 원칙 **  
> 롤백은 어느 계층에서든 **즉시, 예측 가능하게** 수행되어야 한다. DNS 캐싱처럼 통제 불가능한 변수를 “전환/롤백 스위치”로 채택하지 않는다.

## 2. “무중단”의 정의와 허용 기준

무중단이라는 말은 많이 쓰이지만, 정의 없이 쓰면 전환 결과를 성공인지 실패인지 판단할 수 없다. 서비스 SLO 기준으로 아래를 “무중단”의 정량 정의로 확정한다.

| 항목 | 기준 | 의도 |
|---|---:|---|
| 최대 체감 다운타임 | ≤ 3초 | 새로고침 1회 수준 |
| 전환 구간 에러율 | ≤ 0.1% | 300 QPS 기준 전환 순간 일부 실패 허용 |
| p99 지연 증가 | 기준선 대비 2배 이하 | “느려졌지만 장애는 아님” 범위 |
| 세션 영향 | 강제 로그아웃 ≤ 0.5% | 세션/쿠키 이슈 조기 탐지 |
| 데이터 유실 | 0건 | 라우팅 전환이므로 쓰기 유실 불허 |

DB가 동일하게 유지되는 전환이므로 “데이터 유실 0”은 사실상 중복 실행/재시도 설계(POST 재시도 정책, 멱등성 키)에서 갈린다.

## 3. 트래픽 전환 방식 비교 (판정 포함)

트래픽을 레거시에서 신규로 옮기는 방법은 여러 가지가 있다. 각 방식의 특성을 정리하고, 본 문서에서 채택/배제 결정을 명시한다.

### 3.1 DNS 스위칭 (A/CNAME 변경)

| 구분 | 내용 |
|---|---|
| 개념 | DNS 레코드가 가리키는 IP를 레거시 → 신규로 변경 |
| 장점 | 구성 요소 추가 없이 가장 단순 |
| 치명적 단점 | DNS 캐싱은 통제 불가. TTL을 낮춰도 ISP/OS/브라우저가 무시 가능 |
| 롤백 | DNS로 롤백해도 같은 캐싱 문제 반복. 즉시 복구 불가 |
| 판정 | **전환 수단으로 사용하지 않는다 ** |

DNS 스위칭의 가장 큰 문제는 “전환이 끝났다”고 판단할 수 없다는 점이다. TTL을 30초로 설정해도 ISP 리졸버나 운영체제 캐시가 이를 무시하는 경우가 흔하고, 결과적으로 같은 시간대에 어떤 사용자는 레거시로, 어떤 사용자는 신규로 들어오는 “긴 꼬리”가 생긴다. 이 상태에서 장애가 발생하면 원인 분석이 극도로 어려워진다.

### 3.2 Route 53 Weighted / Failover 라우팅

| 구분 | 내용 |
|---|---|
| 개념 | Weighted: 비율 기반 점진 전환 / Failover: 헬스체크 기반 자동 전환 |
| 장점 | DNS 레벨에서 카나리 가능, Failover 시 자동 복구 |
| 핵심 단점 | DNS 캐싱 문제 동일. 가중치 10%가 실제로는 리졸버 단위로 뭉쳐서 들어옴 |
| 운영 문제 | 장애 대응 시 “지금 몇%가 어디로 가는지” 불명확 |
| 판정 | **본 전환 수단에서 제외, 보조 수단으로만 유지 ** |

“카나리 10%”로 설정해도 실제로는 리졸버 단위로 뭉쳐서 들어오기 때문에, 어떤 시점에는 0%일 수도 있고 어떤 시점에는 30%일 수도 있다. 운영자가 전환 비율을 관측/제어하는 감각이 무너진다.

### 3.3 Nginx Upstream 전환

| 구분 | 내용 |
|---|---|
| 개념 | 기존 퍼블릭 Nginx를 유지하고, upstream만 레거시 → 신규로 변경 |
| 장점 | DNS 변경 없이 전환/롤백 가능. `nginx -s reload`로 수 초 내 완료 |
| 단점 | 스위치 레이어가 서버(EC2/Nginx) 설정에 남아 있어 인프라 레벨 표준화가 지연됨 |
| 판정 | **1차 카나리/전환 수단으로 채택 ** |

### 3.4 ALB 기반 Blue-Green / Canary (최종 표준)

| 구분 | 내용 |
|---|---|
| 개념 | Target Group 가중치로 점진 전환 및 즉시 롤백 |
| 장점 | 헬스체크 + 자동 제외 + 연결 드레이닝으로 전환 품질 예측 가능 |
| 롤백 | ALB 가중치 변경으로 수 초 내 즉시 복구 |
| 비용 | 300 QPS 규모에서 운영 가능한 수준 |
| 판정 | **최종 아키텍처의 스위치 레이어/운영 표준으로 채택 ** |

본 문서의 핵심은 “ALB가 좋다/나쁘다”가 아니라, **스위치 레이어를 어디에 두고 어떤 순서로 최종 구조에 도달할 것인가**다. 이 관점에서 ALB Target Group 기반 전환은 최종 표준으로 유지하되, 카나리 시작 시점은 Upstream 전략으로 앞당긴다(섹션 4).

### 3.5 CloudFront / CDN 오리진 스위치

| 구분 | 내용 |
|---|---|
| 개념 | CDN 오리진을 레거시 → 신규로 전환 |
| 장점 | 전 세계 대규모 트래픽, 정적 자산 중심일 때 효과적 |
| 단점 | 동적 API 중심이면 이점 제한적. 캐시/쿠키/헤더 복잡도 증가 |
| 판정 | **본 전환 수단에서 제외 ** |

## 4. Nginx Upstream 방식 vs ALB 먼저 고정 방식 — 비교 및 판정

이 비교의 핵심은 “DNS를 언제 바꾸는가”가 아니라, **스위치 레이어(전환/롤백 스위치)를 어디에 두는가**다.

- **Upstream 방식:** 스위치 레이어가 **EC2(Nginx)** 에 남아 있다.
- **ALB 먼저 고정 방식:** 스위치 레이어가 **인프라 레벨(ALB)** 로 이동한다.

### 4.1 Upstream 방식의 구조적 한계(단점 재정의)

Upstream 방식의 단점은 “SPOF가 남는다”로만 설명하지 않는다. 기존 구조 자체가 이미 단일 인스턴스 기반이므로, 이를 새 리스크처럼 과장하는 논리는 설득력이 약하다. 대신, 아래의 구조적 한계를 명확히 인지한다.

- **스위치 레이어가 EC2(Nginx)에 남아 있는 구조적 한계**  
  전환/롤백 표준이 인프라 레벨이 아니라 서버 설정 레벨(`nginx.conf`)에 머문다.
- **최종 아키텍처 도달이 지연됨**  
  트래픽 스위치가 여전히 서버에 있으므로, “DNS → ALB → TG”라는 최종 경로 검증은 뒤로 밀린다.
- **전환/운영 표준화가 인프라 레벨이 아니라 서버 설정 레벨에 머무름**  
  가중치/헬스/드레이닝 같은 표준 기능이 ALB가 아니라 Nginx 설정으로 구현된다. 운영 표준이 분산된다.

### 4.2 ALB 먼저 고정 방식의 장점(구조적 설명)

ALB 먼저 고정 방식의 장점은 “좋다” 식의 일반론이 아니라, 스위치 레이어 위치가 바뀌면서 생기는 구조적 차이로 정리한다.

- **카나리가 ‘최종 아키텍처 위에서’ 수행됨**  
  사용자 트래픽이 이미 `DNS → ALB`로 진입하므로, 카나리 자체가 최종 경로(헤더 체인, TLS 경계 포함)를 검증한다.
- **스위치 레이어가 인스턴스가 아니라 인프라 레벨(ALB)로 이동**  
  전환/롤백이 서버 재배포나 설정 변경이 아니라, 인프라 구성(Listener Rule/Target Group Weight)으로 통일된다.
- **이후 모든 전환이 Target Group 기반으로 표준화됨**  
  “전환”이 곧 “Target Group 가중치 변경”이 되어, 운영 런북과 관측 방식이 일관된다.

### 4.3 현실적 사례: Upstream 카나리가 ‘최종 구조 전체’를 검증하지 못하는 이유

실제 운영에서 다음과 같은 착각이 발생할 수 있다.

- **ACM 인증서를 ALB에 등록했기 때문에 TLS가 ALB에서 종료된다고 생각했다.**
- 하지만 **실제로는 Nginx가 TLS termination을 수행**하고 있었다.

원인은 간단하다. DNS가 여전히 EC2(EIP)를 가리키는 동안, 사용자 요청은 `:443`에서 Nginx로 들어와 Nginx에서 TLS가 종료된다. 이 상태에서 Nginx가 upstream으로 ALB(또는 신규 엔드포인트)로 프록시하더라도, **사용자 관점의 TLS 경계는 여전히 Nginx**다.

따라서 Upstream 단계에서의 카나리는 아래를 “완전 검증”하지 못할 수 있다.

- TLS termination 위치 변경에 따른 동작(리다이렉트, HSTS, 보안 헤더, 클라이언트 인증 등)
- X-Forwarded-* / client IP 체인 변화
- 퍼블릭 경계(보안그룹, 직접 접근 차단, 리스너 정책)에서의 동작

즉, Upstream 카나리는 “신규 애플리케이션/런타임이 실제 트래픽에서 동작한다”는 검증에는 강하지만, **최종 아키텍처 전체 검증은 DNS가 ALB로 고정된 이후에 완료된다.**

### 4.4 Upstream 방식의 장점

Upstream 방식은 **카나리 시작 시점**에서 매우 강한 현실적 장점이 있다.

- **DNS 캐싱 수렴을 기다릴 필요 없이 즉시 카나리 시작 가능**
- **1단계 전환에 매우 안전하고 현실적인 전략**
- **실패 시 `nginx reload`로 즉시 롤백 가능**
- 반대로, **ALB 먼저 DNS 변경 방식은 DNS 캐싱이 완전히 수렴할 때까지 카나리 테스트 시작이 어렵다**  
  (DNS 변경 직후에는 사용자 유입이 양쪽으로 길게 갈라져, “지금부터가 테스트 구간”을 깔끔하게 정의하기 어렵다)

### 4.5 비교 논리 정리

- **ALB 먼저 DNS 변경 방식:** DNS 수렴 이후 카나리
- **Upstream 방식:** 카나리 먼저 수행 후 DNS는 마지막에 정리
- 따라서 **테스트 시작 시점만 놓고 보면 Upstream이 더 유리할 수 있다.**

### 4.6 판정

**Upstream 방식을 1차 전환 전략으로 선택한다.** 이유는 단순하다.

- **빠르게 실제 트래픽 기반 검증을 시작할 수 있기 때문**이다.

다만, 아래의 구조적 한계를 인지하고 문서에 명시한다.

- 스위치 레이어가 **EC2(Nginx)** 에 남아 있다.
- 최종 아키텍처(특히 TLS 경계/헤더 체인/퍼블릭 경계) 검증은 **DNS가 ALB로 고정된 이후** 완료된다.

따라서 다음 점검을 **별도 계획(Phase 3)** 으로 포함한다.

- TLS 경계(TLS termination) 재검증
- X-Forwarded-* / client IP 헤더 체인 검증
- 퍼블릭 경계 동작(직접 접근 차단, 리스너 정책, 리다이렉트) 검증

이 결정은 단일 리전, 수백 QPS 규모에서 “전환 안전성”과 “검증 착수 속도” 사이의 현실적 균형으로 정리한다.

## 5. 현재 / 목표 아키텍처

### 5.1 현재 구조

```text
User
  ↓
DNS (service.example.com)
  ↓
EC2 (EIP) :443
  ↓
Nginx (reverse proxy + TLS termination)
  ↓
Spring Boot (:8080)
  ↓
RDS MySQL

```
5.2 전환 중간 구조 (Upstream 카나리 단계)
```text
User
↓
DNS (service.example.com)
↓
EC2 (EIP) :443
↓
Nginx (TLS termination + Switch Layer: upstream weight)
├─ Legacy Spring Boot (:8080)
└─ New Endpoint (ALB or ASG behind it)
↓
RDS MySQL (동일)
```
5.3 목표 구조 (최종)
```text
User
↓
DNS (service.example.com)
↓
ALB :443 (TLS termination, Switch Layer: Target Group weight)
↓
Target Group (Weighted Routing)
├─ TG-Legacy: 기존 EC2 (Nginx + Spring Boot)  [전환 기간 한시적 유지]
└─ TG-New: 신규 ASG (Spring Boot)
↓
RDS MySQL (동일)
```
## 6. Phase 0 — 사전 점검

무중단 전환의 대부분은 전환 전에 결정된다. 전환 구간에는 레거시와 신규가 동시에 살아있게 되는데, 사고가 나는 지점은 정해져 있다.

### 6.1 세션/상태

서버 메모리에 세션을 저장하고 있다면, 전환 시 사용자가 강제 로그아웃되거나 상태가 초기화될 수 있다.

- 우선순위 1: JWT 등 무상태 방식으로 전환
- 우선순위 2: Redis 세션 스토어(Spring Session)로 외부화

LB 스티키 세션은 사용하지 않는다   
카나리/롤백 시 분산이 왜곡되어 관측/판단이 어려워진다.

### 6.2 배치/스케줄러/컨슈머 중복 실행

현재 코드 기준(2026-03-02 점검) 배치/스케줄러/컨슈머/잡 동작은 확인되지 않았다. 즉, 이 단계에서의 중복 실행 리스크는 현재 낮다.

향후 잡/스케줄러/컨슈머를 추가할 경우:
- 잡은 전용 워커로 분리
- DB/Redis 락으로 리더 선출
- 전환 구간에는 Feature flag로 비활성화

### 6.3 스키마 호환성

신규 앱이 DB 스키마 변경을 동반한다면, 레거시와 동시 운영 중 충돌이 발생할 수 있다.

- 원칙: Backward compatible migration
- 컬럼 추가: 양쪽 앱 모두 동작하도록 설계
- 컬럼 제거/타입 변경: 전환 완료 후 마지막에 수행

## 7. Phase 1 — 신규 환경 구성 및 관측 가능성 확보

### 7.1 신규 ASG 환경 준비

신규 ASG에 Spring Boot 앱을 배포하고, RDS는 기존과 동일하게 유지한다.

- /health: liveness
- /ready: DB 커넥션 풀 등 필수 의존성 확보 후에만 200

/health가 너무 얕으면 “헬스체크는 OK인데 실제는 장애”가 발생한다.

### 7.2 버전 식별 (필수)

전환 중 “어느 요청이 레거시/신규에서 처리됐는지”가 보이지 않으면 검증이 불가능하다. 응답 헤더로 식별한다.

```nginx
# Nginx 예시
add_header X-Backend-Env "legacy" always;   # 레거시
add_header X-Backend-Env "new" always;      # 신규

# 배포 버전 식별
add_header X-Release "2026-03-02-1" always;
```

## 8. Phase 2 — Nginx Upstream 카나리 전환 (Runbook)

이 단계에서 스위치 레이어는 EC2(Nginx)에 존재한다. 목표는 “실제 트래픽 기반”으로 신규 환경을 빠르게 검증하는 것이다.

### 8.1 Warm-up

전환 1~2분 전, 신규로 읽기 트래픽(GET)만 소량 흘려서 JVM JIT 컴파일, 캐시 워밍, 커넥션 풀 확장을 선소진한다. 멱등성 설계가 완비되지 않았다면 쓰기 포함 카나리는 금지한다.

### 8.2 전환 시퀀스

- 신규 ASG(또는 신규 ALB 엔드포인트)가 정상(ready)인지 확인
- Nginx upstream에 신규 엔드포인트를 추가
- 업스트림 가중치로 카나리 시작: 99/1 → 95/5 → 75/25 → 50/50 → 0/100
- 각 단계 5~10분 관측 후 다음 단계 진행
- 임계치 초과 시 즉시 롤백(섹션 8.3)

운영 규칙   
전환 단계는 “정해진 시퀀스”로 고정하고, 현장 재량으로 비율을 바꾸지 않는다. 관측 지표(섹션 11) 초과 시에는 단계 진행이 아니라 즉시 롤백을 우선한다.

### 8.3 롤백

실패 시 Nginx upstream을 레거시 100%로 되돌리고 nginx -s reload 로 즉시 반영한다.

이 롤백은 DNS 캐싱과 무관하게 수 초 내 완료된다.

## 9. Phase 3 — ALB 고정 엔드포인트 설치 + 최종 구조 검증 (DNS 1회 변경)

Upstream 단계에서 신규 환경을 실제 트래픽으로 검증했더라도, 최종 구조 전체(TLS 경계/헤더 체인/퍼블릭 경계) 는 아직 검증되지 않았을 수 있다(섹션 4.3). 이 단계에서 스위치 레이어를 ALB로 이동시키고 최종 경로를 확정한다.

### 9.1 절차

- 퍼블릭 ALB 생성 + HTTPS 리스너 + ACM 인증서 연결
- TG-Legacy 생성, 기존 EC2 등록(전환 기간 즉시 회귀 경로 확보 목적)
- TG-New 생성, 신규 ASG 등록
- 사전 검증: ALB DNS 이름으로 직접 호출하여 TLS/헤더/리다이렉트 동작 확인
- DNS를 EC2 EIP → ALB DNS name으로 1회 변경 (저트래픽 시간대, 사전 TTL 하향)
- DNS 수렴 관측(긴 꼬리 포함) 후 최종 구조 검증 완료 판정

### 9.2 TLS 종료 위치 변경 점검

이 단계에서 TLS termination이 Nginx → ALB 로 이동한다. 아래를 반드시 점검한다.

- X-Forwarded-Proto, X-Forwarded-For 체인 변화에 따른 앱 동작
- 리다이렉트 로직
- HTTPS 강제
- 인증/콜백 URL 검증
- 퍼블릭 경계 동작
- 기존 EIP 직접 접근 차단 여부
- ALB → EC2 인바운드 허용 여부(전환 기간 한시 운영 포함)

사례 기반 주의점   
ACM 인증서를 ALB에 등록해두었다고 해서, Upstream 단계에서 TLS가 ALB에서 종료됐다고 가정하지 않는다. DNS가 EC2를 가리키면, 사용자 트래픽의 TLS termination은 여전히 Nginx일 수 있다.

### 9.3 이 단계의 리스크를 낮추는 이유

Upstream 단계에서 신규 런타임 자체는 이미 실제 트래픽으로 검증을 끝냈다.

Phase 3의 핵심 리스크는 “앱 기능”이 아니라 경계(TLS/헤더/퍼블릭) 이동에 집중된다.

따라서 이 단계의 작업 범위를 경계 검증에 한정하고, 장애 시에는 ALB Target Group을 통해 즉시 회귀한다(아래 섹션 12).

## 10. Phase 4 — 스위치 레이어 표준화 및 레거시 제거

DNS가 ALB로 고정된 이후에는, 전환/롤백의 표준 스위치를 ALB Target Group 가중치로 통일한다.

- (전환 기간) TG-Legacy 100 / TG-New 0
- (검증 후) TG-Legacy 0 / TG-New 100
- 안정화 이후 레거시 EC2(EIP/Nginx 포함) 단계적 제거

이로써 스위치 레이어는 서버 설정에서 인프라 레벨로 완전히 이동하고, 이후 전환은 Target Group 기반으로 표준화된다.

## 11. 전환 중/후 모니터링

전환 전/중/후에 K6 등으로 지속 부하를 걸어 “무중단”을 계량한다. 응답 헤더의 X-Backend-Env 를 수집해서 신규로 얼마나 갔는지를 실제로 검증한다.

### 11.1 장애 감지 기준

| 지표 | 정상 | 경고 | 장애 (즉시 롤백 후보) |
|---|---|---|---|
| 에러율 | < 0.01% | 0.01~0.1% | > 0.1% |
| p99 | < 2x baseline | 2~3x | > 3x |
| 5xx | 0 | 소량 | 지속 발생 |
| 헬스체크 실패 | 0 | 간헐 | 연속 실패 |

## 12. 예상 문제와 대응

| 문제 | 발생 조건 | 대응 |
|---|---|---|
| 세션 로그아웃 | 현재 서버 메모리 세션 미사용 | 상태 유지 요구 시 세션 외부화/무상태화 설계를 선결 |
| 헬스체크 OK, 실제 장애 | /health가 너무 얕음 | /ready에 DB/필수 의존성 포함 |
| POST 재시도 중복 | 프록시/LB 재시도 설정 | POST 재시도 금지 또는 멱등성 키 |
| WebSocket 끊김 | 전환/드레이닝 | 드레이닝 / 재연결 로직 / 점진 전환 |
| 헤더/스킴 불일치 | TLS 종료 위치 변경 | X-Forwarded-* 처리 점검 |

## 13. 롤백 전략

롤백은 기술보다 판단 기준이 중요하다. 전환 단계별 롤백 스위치를 분리해 명확히 한다.

### 13.1 Phase 2(Upstream) 롤백

Nginx upstream을 레거시 100%로 변경 후 nginx -s reload

반영: 수 초 내

### 13.2 Phase 3~4(ALB) 롤백

ALB Target Group 가중치로 회귀

예: TG-Legacy 100 / TG-New 0

반영: 수 초 내 (DNS 캐싱과 무관)

롤백의 원칙   
DNS 롤백은 느리고 예측 불가하므로, 롤백 스위치는 항상 프록시/LB 계층에 둔다. 본 계획에서는 Phase 2는 Nginx, Phase 3 이후는 ALB가 그 역할을 맡는다.

## 14. 체크리스트

### 14.1 사전 준비

- 신규 환경 /health, /ready 엔드포인트 준비 및 실제 의존성 포함
- 응답 헤더 X-Backend-Env 로 레거시/신규 구분 가능
- 세션/캐시 미사용 상태 확인, 파일스토리지 외부화 여부 확인
- 현재 잡/컨슈머 동시 실행 항목은 미정의 상태. 도입 시(락/분리/리더 선출/Feature flag)로 전환 리스크 통제
- Grafana/CloudWatch에서 레거시 vs 신규 비교 가능
- 전환/롤백 스위치가 Phase 2는 Nginx, Phase 3 이후는 ALB 1곳으로 단일화되어 있는지 확인

### 14.2 Phase 2: Upstream 카나리

- 신규 warm-up 수행 (GET only)
- readiness 체크 연속 성공 확인
- 에러율/지연 기준선(Baseline) 확보
- Upstream 가중치 단계적 변경 + 각 단계 관측
- 장애 기준 초과 시 즉시 nginx reload 롤백

### 14.3 Phase 3: ALB 고정 + 최종 구조 검증

- ALB 생성 + HTTPS 리스너 + ACM 인증서
- TG-Legacy에 기존 EC2 등록 및 헬스체크 통과
- TG-New에 신규 ASG 등록 및 헬스체크 통과
- DNS 변경 (EC2 EIP → ALB) 저트래픽 시간에 1회 수행
- TLS 경계/헤더 체인/퍼블릭 경계 동작 검증 완료

### 14.4 전환 후

- 30~60분 관측
- 레거시 환경을 “바로 되돌릴 수 있는 상태”로 최소 24~72시간 유지
- 안정화 후 레거시 단계적 제거

이 문서는 DB 마이그레이션에서 역복제로 보장한 “즉시 롤백”과 같은 안전성 수준을 인프라 전환에서도 유지하기 위한 실행 계획이다. 다만 카나리 시작 시점을 앞당기기 위해 Upstream 방식을 1차 전략으로 채택하고, 최종 구조 검증과 운영 표준화는 DNS를 ALB로 고정한 이후에 완료한다.
