## 1. 보고 목적

이 문서는 마이그레이션 계획서(`migration-plan.md`)의 실행 가능성을 리허설로 검증한 결과를 정리한다.

검증 대상은 세 가지 핵심 질문이다.

1. 계획서의 **Phase 0~4 단계가 실제로 실행 가능한가?**
2. 단계별 **SLO와 임계치(Section 11, 14)를 실측 지표로 판정할 수 있는가?**
3. 장애 발생 시 **원인을 분리하고 롤백 판단을 내릴 수 있는가?**

## 근본 목적

이 문서는 무중단 마이그레이션을 단계적으로 실행하기 전, 장애 전파 구간의 실증 데이터와 롤백 판단 근거를 확보해 리스크를 줄이기 위한 의사결정 지원 문서이다.

### 보고 범위

- 검증 대상: Phase 0(사전 점검), Phase 2(카나리 전환), Section 11~14(모니터링·롤백·체크리스트)
- 제외 대상: DB 무중단 전환 실험(`migration/database` 별도 보고서)

## 비목적

이 보고서는 설계 변경 제안, 비용 산정, 포스트모템 분석이 아니라 `migration-plan.md`의 **실행 정합성 및 전환 게이트 검증**에 한정한다.

## 3. 시나리오별 실행 결과

### 3.1 시나리오 A — 베이스라인 (전환 없음)

#### 이 실험이 검증하는 것

트래픽 100%가 기존(legacy) 서버로만 가는 상태에서 에러율과 응답시간의 "기본선"을 확보한다. 이 기본선이 0에 가까워야, 이후 전환 시나리오에서 발생하는 에러를 "전환 때문"이라고 원인 분리할 수 있다.

#### 실행 조건

- Nginx 업스트림: legacy 100%
- 부하: RPS 8, 2분간 지속

#### 결과

| 지표 | 값 |
|---|---|
| 총 요청 수 | 1,195 |
| 체크 통과율 | 100.00% (961/961) |
| 에러율 (read) | 0.00% |
| 에러율 (total) | 0.00% |
| HTTP 요청 실패율 | 0.00% |
| 다운타임 | 0ms |
| 응답시간 p95 | 18.17ms |

#### 판단

전환이 없는 상태에서 요청 처리 체계가 안정적임을 확인했다. 에러율 0%로 기준선 확보에 성공하여, 이후 시나리오에서 발생하는 에러는 전환 또는 장애 실험에 기인한 것으로 판단할 수 있는 분석 토대가 마련되었다.

---

### 3.2 시나리오 B — 카나리 전환 (legacy 90% / new 10%)

#### 이 실험이 검증하는 것

계획서 Phase 2의 카나리 전환을 최소 비율(10%)로 실행하여, 트래픽 일부를 신규 서버로 보냈을 때 즉시 장애가 발생하는지 확인한다. 에러율이 임계치(0.1%) 아래로 유지되면 1차 합격 신호로 판단한다.

#### 실행 조건

- Nginx 업스트림 가중치: legacy 9 (90%) / new 1 (10%)
- 부하: RPS 8, 2분간 지속

#### 결과

| 지표 | 값 |
|---|---|
| 체크 통과율 | 100.00% |
| 에러율 (read) | 0.00% |
| 에러율 (total) | 0.00% |
| HTTP 요청 실패율 | 0.00% |
| 다운타임 | 0ms |
| 응답시간 p95 | 16.12ms |

#### 판단

카나리 초기 단계(90:10)에서 가중치 혼입이 에러 급증으로 이어지지 않았다. 에러율 0.00%는 계획서의 임계치(0.1%)를 충족하며, 베이스라인(시나리오 A)과 비교해도 지표 악화가 없다. Phase 2 카나리의 1차 합격 조건을 만족한다.

---

### 3.3 시나리오 C — 장애 유발 (단일 컨테이너 강제 중단)

#### 이 실험이 검증하는 것

실제 장애가 발생했을 때, 계획서 Section 11(모니터링)과 Section 13(롤백)이 동작하는지 확인한다. 구체적으로 두 가지를 검증한다.

1. **장애 감지**: 어떤 레이어에서 문제가 발생했는지 ALB TG 상태와 k6 지표를 통해 분리 추적할 수 있는가?
2. **롤백 판단**: 관측된 데이터를 기반으로 즉시 롤백 결정을 내릴 수 있는가?

#### 실행 조건

- Nginx 업스트림: 시나리오 B와 동일 (legacy 90% / new 10%)
- 장애 유발: 신규 ASG 인스턴스(`10.0.1.15`)에서 `docker stop billage-rehearsal-be` 실행
- k6 부하는 장애 유발 중에도 계속 유지
- ALB Target Group 상태를 타임라인과 동기화하여 모니터링

#### 결과

- 신규 서버로 라우팅되는 요청에서 **502 에러 즉시 발생**
- 다운타임은 **512~567ms 수준의 단발성 장애**로 관측 (연속 장애로 확산되지 않음)
- ALB Target Group 상태 전이(`draining → initial → inservice`)가 응답 이상 징후 타임라인과 정확히 일치
- 신규 서버 비중이 10%이므로 전체 트래픽 관점에서 체감 영향은 제한적

#### 판단

장애 발생 시 "어떤 레이어가 깨졌는지"를 ALB TG 상태 전이와 502 발생 타임라인으로 분리 추적할 수 있었다. 이는 롤백 판단을 자동·수동 모두 빠르게 지원할 수 있음을 의미한다.

다만 신규 서버 비중이 더 커지거나 동시 교체·재배포가 겹치면 장애 체감이 증가할 수 있으므로, 비율 확대 시 동일 실험을 반복할 필요가 있다.

## 5. 리스크 분석

### 현재 확인된 리스크

1. **502 단발성 장애**: 회복이 빨라 임계치 위기는 아니나, 신규 비중 확대 시 빈도 증가 가능성 있음
2. **전환 비중 확대**: 10%에서는 안정적이었으나, 25% 이상에서는 사용자 체감 영향이 증폭될 수 있어 추가 검증 필요
3. **다중 인스턴스 미검증**: 단일 신규 인스턴스 환경에서만 검증되어, 다중 인스턴스 failover 특성은 추후 확장 필요

## 6. 종합 판정

### 판정 결과

`migration-plan.md`의 핵심 가정은 이번 리허설에서 실증되었다.

- 베이스라인은 안정적이다.
- Phase 2 카나리(legacy 90%, new 10%)에서 오류율·장애 지표가 기준 내에 있다.
- 장애 유발 시 원인 분류와 롤백 판단을 위한 관측 루프가 실제로 동작한다.

### 다음 단계 진행 조건

Phase 2 1차 게이트 조건은 충족되었으며, 다음을 선행한 후 비율 확대 단계로 진행을 권장한다.

1. 10% → 25% → 50% → 100% 혼입 시나리오를 연속 실행하여 각 구간별 안정성 확인
2. ASG 인스턴스 2개 이상 환경에서 동일한 장애 유발 실험 반복
3. Phase 3(TLS·헤더 체인·퍼블릭 경계 변경) 전까지 현재 측정 기준을 그대로 유지

## 7. 향후 과제

- 베이스라인 + 전환 쌍 실행을 시나리오별 표준 템플릿으로 고정
- 에러율 외에 다운타임·TG 상태 전이를 동시 수집하는 로그 체계 강제화
- 비율별 장애 유발 패턴(10% → 25% → 50%)을 사전 등록
- 운영 대시보드에는 통일된 측정 기준의 최종 판정값만 반영
